# Removable CRM starter configuration

Ship one explicit, versioned starter package for the first general CRM journey. Installing it copies workspace-owned definitions: a Sales opportunity pipeline with New/Qualified/Proposal/Won/Lost stages, a General deal category with Planned/Active/Completed statuses, Note/Interaction activity types, a Follow-up task type, a Review requirements task template, a one-step coordination checklist and a rule that schedules it on transition into Active. The task uses the deal owner and a zero-day UTC calendar offset. None of these statuses or steps is required for other workspace workflows.

Installation is a deliberate API/CLI/MCP/web operation, never an automatic side effect of enabling CRM or upgrading the deployment. At most one active installation of this package exists per workspace. Explicit reinstallation after removal creates new definitions and retains the old installation evidence. The package version and typed definition references are recorded; users edit copied definitions through their existing operations.

Installation, configuration audit/history, provenance and retry results commit atomically through module-owned transaction providers. CRM cannot write Tasks tables directly. The caller needs CRM configuration read/manage and Tasks configuration read/manage. Replays recheck those current grants and enabled state. A failure halfway through installation leaves no partial configuration.

Removal archives unchanged package definitions and retains business instances, histories, revisions, tasks, opportunities, deals and activities. It does not erase configuration or reinstall anything. Definitions modified since installation are retained. Unchanged definitions that active customized configuration still depends on are also retained: custom rules protect their checklist/status, active checklists protect task specifications in all retained revisions, active task templates protect the types in all retained revisions (older revisions remain explicitly usable), and retained/new stages/statuses protect their parent pipeline/category. Ordinary business-record references do not prevent archival because those records and history remain valid.

Removal runs in dependency order in one workspace-serialized transaction. Each decision is returned as archived, already archived or retained with a reason. Configuration providers perform their own authorization and version checks. Pending jobs that reference a retired definition become visibly blocked on execution; retained job evidence is not deleted. A removed package's definitions can still be managed manually, and customizing one package must not alter another installation.

Expose package information, bounded installation history/detail, install and remove through all four interfaces. The web page explains the defaults and removal policy before an action, retains rejected expected versions/retry keys, links to copied definitions and shows retained customization. Tests cover untouched removal, modified definitions/dependent retention, explicit reinstall, safe retries and concurrent installs, scope/module denial, rollback late in install/removal, preserved live/past business instances and queued work, typed workspace constraints and browser/API/CLI/MCP parity. Existing CRM and Tasks regressions must still pass after transaction-provider extraction.
