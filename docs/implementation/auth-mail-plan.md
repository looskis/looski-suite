# Authentication email implementation plan

Continue the approved Supabase identity boundary with provider-neutral SMTP, magic-link sign-in and password recovery. Supabase owns token issuance, expiry, one-time verification, sessions and password changes. No implicit signup or membership creation is permitted. The public browser server accepts same-origin forms; raw Auth administration remains private.

An installation selects disabled mail, private local-development capture, or an external SMTP server with verified implicit TLS on port 465. Port 587 is rejected because the pinned upstream mailer cannot enforce STARTTLS. Credentials remain in private installation files and are mounted only into Auth. Configure a fixed public origin and custom templates served privately before Auth starts. Production credentials and a real public hostname remain operator inputs; local success does not claim Cloudflare or hosted validation.

An emailed URL first moves its token into a short-lived HttpOnly pending cookie and redirects to a clean confirmation page. GET never consumes the Supabase token. Explicit same-origin POST verifies it, creates the existing HttpOnly session, and redirects to workspaces or password replacement. Token-bearing redirects use no-referrer; the confirmation page uses same-origin, because no-referrer makes browsers post `Origin: null`, which the same-origin check refuses. All use no-store. Failed, expired or reused links expose no provider details or tokens. Password replacement requires an authenticated session and same-origin POST.

Verification uses the previously approved public browser/HTTP seams, real Supabase and a private SMTP capture fixture: delivery and canonical URL, no implicit account creation, prefetch safety, clean URL and cookies, reused/expired links, recovery and new-password login, CSRF and redirect rejection, disabled mail and account-neutral unavailable delivery, with credential-free operator diagnostics. Configuration validation is exercised through setup. Full regression runs sequentially per fixture, then standards/spec review and a signed checkpoint. Invitations follow as a separate application membership lifecycle.
