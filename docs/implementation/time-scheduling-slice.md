# Milestones 7 and 8 — time tracking and scheduling

Implementation checkpoint, November 1, 2026. Schema 35 adds Time tracking; schema 36 adds Scheduling and durable job due times. Both are independently selectable per workspace. The accepted scope is the [build plan](../build-plan.md); external calendar synchronization and the future OAuth release gate are separate work.

## Time tracking

Members create manual entries or start their own timer, with a description, work date, billable flag and optional project. One running timer per member is enforced by a partial unique index. Pause and stop bank elapsed milliseconds once; resume starts another segment. Workspace locking, optimistic versions and request fingerprints protect concurrent changes and retries. Stopped entries can be corrected or archived. Timer ownership cannot be reassigned; only the owner operates a timer, while workspace managers can correct stopped entries.

The stored work date assigns the whole entry to a reporting period, including work crossing midnight. Reports sum the same visible, non-archived entries and filters as the entry list, with separate billable totals. Running duration is calculated at the read transaction's timestamp. Timers survive process restarts and keep measuring elapsed time while the application is disabled. Paused time does not accumulate. The browser explains that running totals update on refresh.

`time.read` and `time.manage` support workspace and assigned (own membership) scope. Project references are checked through Projects' interface. Hidden or disabled project associations are omitted, while independently owned time remains readable. Project-filtered reports require project access. Unassigned work requires no other application. Budgets define a date range, optional project and optional billable-only selection; a projectless budget includes all work. Budgets require workspace-wide time reads, and changes additionally require workspace-scoped `time.budgets.manage`.

Web, HTTP, `looski time` and nine `time_*` MCP operations cover entries, timer transitions, totals and budgets. CLI list/report support project, dates and billable filters. JSON exports `time_entries` and `time_budgets` use those same read policies. Durations are integer milliseconds, never rounded hours; displayed hours are presentation only. Money rates, invoicing, approval sheets, automatic idle detection, task-level association and payroll are outside this milestone.

## Scheduling

Staff create appointment types on their own host calendar. Availability consists of weekly local-time windows plus date exceptions that replace that day's weekly hours. Types specify an IANA timezone, fixed elapsed duration, before/after buffers, optional versioned Forms intake, an optional CRM mapping, and optional attendee reminders. Closing or archiving a type stops new bookings; existing reservations and history remain.

Public pages show available starts on a 15-minute grid, up to one year ahead. UTC enumeration handles skipped and repeated local times; every occupied minute, including buffers, must fall in local availability. Slot labels include the timezone and UTC offset. The same host's appointment types share one exclusive calendar. A PostgreSQL exclusion constraint rejects overlapping buffered intervals, and booking mutations serialize on the workspace lock. Availability changes affect future selection without moving existing appointments. No claim is made about calendars outside this installation.

A confirmed reservation, its versioned Forms submission (when attached), their association and an immutable booking event commit in one transaction. Validation failure or event-write failure rolls all of them back. `forms::booking_submit` reuses Forms validation but deliberately starts no standalone Forms recipe or notification. A stale displayed form version is rejected before confirmation. Basic attendee name/email works with both Forms and CRM disabled.

The customer saves the booking address and a random 256-bit access code. Only its digest is stored. API requests use `X-Booking-Key`; the browser uses an HttpOnly, SameSite=Strict cookie confined to that appointment path. Codes never enter URLs, audit, business exports or job payloads. Public DTOs omit internal intake, CRM and host information. Possession grants access to that reservation, not identity or staff authority. Public calls are throttled; browser mutations require same origin. Cancellation and rescheduling use versions and retry fingerprints, retain the appointment/submission/CRM association, and append history. Cancellation never deletes a contact. Customer code rotation/recovery, general customer accounts, payment, group capacity, round-robin routing and external calendar synchronization are not included.

`scheduling.read`, `scheduling.manage` and `scheduling.recipes.manage` support workspace or assigned (host membership) scope. A customer code never becomes an ActorContext. Forms answers, Contacts/intake references and CRM opportunities each retain the owning module's current read policy. Contact timelines independently compose visible booking events and authorized intake answers, including contact merge families. Staff business operations have web/API/CLI/MCP coverage; anonymous capability operations are web/API only. Exports include `appointment_types`, `appointments` and parent-scoped `appointment_events`; the appointments archive selection means cancelled reservations.

## Booking follow-up and reminders

A booking snapshots its approved CRM field mapping and queues one `scheduling.crm_inquiry` job. The worker uses current recorded-member permissions, shared Contacts intake resolution and CRM's inquiry/participant interfaces. The basic fields are `attendee_name` and `attendee_email`; optional form mappings must match published question types. Those two keys are reserved in CRM-connected custom intake. Public answers never overwrite an existing contact. Ambiguous resolution waits for review; the appointment page links to Intake review and supports a new attempt after resolution.

Intake creation, inquiry creation, participant association and job completion use one transaction. The appointment stores committed progress and completed effects. A failed job leaves the confirmed booking intact, with a visible error code and explicit retry operation. Disabling Scheduling or CRM blocks pending dependent jobs; disabling Forms blocks only custom-intake booking recipes. Re-enabling a module does not silently resume blocked work. Retry requests reauthorize the caller; workers reauthorize the recorded actor.

Reminder jobs have a durable `available_at` timestamp and an appointment generation. Early queue messages are deferred before consuming attempts, including after an administrator resumes a job. At delivery, the worker rechecks authority, Scheduling state, generation, cancellation and whether the start is already past. Cancelled or superseded generations are skipped. SMTP uses the existing installation transport and local Mailpit fixture. As with existing notification mail, delivery is at least once: a crash after SMTP acceptance but before the database commit can repeat a reminder. External mailbox deliverability remains an installation release gate.

- `scripts/time_smoke.py`: standalone operation, exact timer conservation, transition race, budgets, project authorization, scoped totals/exports and CLI/MCP.
- `scripts/scheduling_smoke.py`: exclusive slot race across types, buffers, availability exceptions, London DST gap/fold, scoped staff access, atomic failure injection, embedded recipe suppression, worker restart, CRM failure/repair, explicit module resume and reminder generation fencing with local SMTP delivery.
- `scripts/time_scheduling_browser_smoke.py`: server-rendered entries/budgets, type editor, intake validation, private-cookie isolation, escaping, cancellation and CSRF.
- `scripts/time_scheduling_chrome_smoke.mjs`: real Chrome editor/submissions, custom intake, reschedule/cancel, stored-markup probes and mobile overflow. Review screenshots are in `/tmp/looski-{time-staff,scheduling-staff,booking-mobile}.png`.
- Export coverage and the coordinated restore rehearsal include both applications. The restore checks exact milliseconds, budgets, versioned intake association, reservation history, customer code scope and quarantined reminders.

There is no bulk historical appointment import. Manual time can be created through its ordinary API/CLI/MCP contract; booking creation uses current availability and intake. Portable backup/restore preserves historical state.
