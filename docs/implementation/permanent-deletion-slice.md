# Controlled permanent-deletion checkpoint

Schema 26 adds minimal deletion receipts and invalidated replay tombstones. Archived, unmerged contacts can be permanently deleted only with current independent read/deletion scopes, explicit ID confirmation, expected version and idempotency key. Restrictive foreign keys preserve business references and history; the operation never cascades into other modules or Auth. It removes only owned identifier associations and now-orphan identifiers, redacts stale Contact replay payloads and records identifier-free audit attribution atomically. See [the reference/retention policy](permanent-deletion-plan.md).

API, CLI, MCP and browser journeys passed on upgraded and clean-install fixtures. Evidence covers active/merged/referenced conflicts, hidden ownership, separate destructive authority, replay authority after revocation, concurrent identical requests, shared/orphan identifiers, retained organization history and aliases, invalid confirmation/version, and late-audit rollback. Review found an identifier/row lock inversion with editing; a forced overlap failed on the old image (delete 200/edit 503) and passed after identifier-before-row locking with a version recheck. Both reviewers found the correction sound. Full implemented-capability regression passed on both fixtures after the correction; static checks and unit tests passed.

No automatic purge, global personal-data erasure, backup expiry policy or permanent deletion of other record types is implied. This checkpoint remains in the user's requested single remaining signed commit.
