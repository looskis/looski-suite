# CRM relationship increment

CRM owns separate opportunity/deal contact and organization participant tables, plus separate tag assignment tables. Each reference has a workspace-qualified foreign key. Participant role is a workspace-entered label, not an authorization role. Each record can have at most one primary contact and one primary organization. Parent version protects relationship changes and audit/replay commits with the change.

Relationship reads intersect the sales record's read scope with the referenced Contacts record's independent read scope. Hidden participant IDs, names and counts must not leak. Use Contacts-owned projection functions within the caller's transaction rather than CRM reading Contacts tables directly. Existing contact aliases resolve through the survivor only when both alias and survivor are visible; association history keeps the original reference. New associations use the canonical contact ID. Confirmed merges preserve references without silently transferring login access or rewriting historical source evidence.

Participant operations are individual upserts/removals rather than full-list replacement, so an editor cannot erase hidden associations by saving only the visible subset. Each call needs the corresponding CRM participants permission and sales-record read, plus independent participant read authority. Primary promotion/replacement uniformly requires workspace-wide read of that participant type; scoped users may demote/end an already visible primary without inspecting other associations. Omitted is_primary preserves its state. Archived records/participants may lose associations but cannot receive new ones; existing links remain readable. Bounded lists apply independent visibility before pagination.

Tags reuse the workspace catalog and existing archive/retention policy. CRM authorizes and owns assignment operations. Tags never grant access. Record lists support tag filtering before pagination, and disabled CRM denies relationship operations as well as record operations. API, CLI, MCP and server-rendered pages expose the same operation semantics.

Acceptance: visible/hidden/cross-workspace participants; primary replacement; alias/survivor reads after merge; archive retention; stale versions and concurrent primary assignment; idempotent retry after current authority changes; exact scoped tag filtering; audit rollback; module disable; representative browser and CLI/MCP paths. Coordination tasks and templates remain the next increment.

Concrete operations use stable association IDs: POST adds an immutable reference, PATCH edits metadata or ends/restores that association, and a scoped history endpoint returns immutable snapshots. Each association retains its original reference through contact merge; visible aliases resolve to their current survivor. Merge-induced canonical duplicates retain distinct role/history records until explicitly ended. Add/restore rejects canonical duplicates only among visible associations, so an inaccessible alias does not become an existence oracle. Exact original references remain unique per parent. Restoration is a new active assignment for archive and duplicate checks.

Participant list queries scan bounded candidate batches until collecting the requested number of visible results plus one or reaching exhaustion. Only visible association IDs form public cursors. No candidate-scan cap may silently omit later visible records. Archive and merge races may overlap an association write; foreign keys preserve the original reference, and every later read re-resolves aliases and reapplies current independent permissions. Historical snapshots record association metadata, not copied contact private fields.

Mutation reference resolution acquires the Contacts merge advisory lock before locking original/canonical contact rows in UUID order, or locks the organization row, then rechecks current visibility/archive/canonical state. CRM and access-administration workspace serialization uses `FOR NO KEY UPDATE`: it still serializes administration/module writes, while allowing FK key-share locks needed for concurrent Contacts audit inserts. This prevents a workspace-row/contact-row lock cycle. A participant write holds the reference locks until its audit/history/replay transaction commits.
