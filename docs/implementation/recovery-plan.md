# Local recovery implementation plan

Implement the accepted release requirement for coordinated encrypted backup and an isolated restore rehearsal. The earlier daily schedule, automatic retention, external destination and RPO proposals remain undecided; initial tooling is manual and never automatically deletes archives.

Use the pinned PostgreSQL custom-format dump for authoritative application/Auth/PGMQ/file data. Include an explicit roles recovery recipe, deployment/source/migration manifest and required installation secrets. Capture actual queue tables and verify them, rather than assuming extension metadata retains pending messages. Freeze source inputs and verify migration identity before claiming update recovery.

Use the existing installation setup lock; stop every active writer including Auth and workers before capturing the database. Preserve the original running-service set and attempt to restart exactly those services on completion or failure. Show maintenance duration and failures. The runner is a host-side operation independent of the application queue. Private temporary files are mode 0600 inside mode 0700 directories.

Encrypt with pinned age 1.3.2 and an explicit age recipient. The owner retains the decryption identity separately; never package that identity in its own backup. Docker runs the encryption utility with networking disabled and no write mounts. Verify official release archive SHA-256s in the image build. Write encrypted output to a temporary file, sync and publish without overwriting any existing destination. Never publish unauthenticated decrypted data or extract before decryption/integrity verification succeeds.

Restore only to a fresh, distinct installation with fresh volumes and an internal Docker network. Preserve the original source installation. Start only the database initially, restore compatible roles/schema/data, validate counts and file checksums, and quarantine pending external-effect jobs. Auth sessions must be invalidated and identity signing material replaced before exposing the recovery instance. Outbound mail and workers remain disabled; no routing switch or automatic job resumption. Rehearsal can expose a loopback-only verification UI after isolation checks. Opening recovery to production remains a separate explicit operation after reconciliation.

Test interrupted/truncated/tampered encryption, wrong key, archive path/link rejection, existing-destination protection, late backup failure with service restoration, clean isolated Auth/business/file/queue recovery, incompatible source/version rejection, and update failure leaving the prior archive usable. Measure real fixture archive size, maintenance time and restore time. A same-disk fixture archive is not off-machine protection.

Sources: [age 1.3.2](https://github.com/FiloSottile/age/releases/tag/v1.3.2), [age usage](https://github.com/FiloSottile/age/blob/v1.3.2/README.md#usage), [PostgreSQL 17 pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html), [PostgreSQL 17 pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html). The tool design above is our implementation choice; restore compatibility still requires measured evidence.
