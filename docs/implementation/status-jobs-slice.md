# Status rules and durable jobs checkpoint

Schemas 20–21 introduce the first bounded queued recipe: a material deal-status transition schedules a pinned coordination revision. Initial creation in a status, ordinary edits and status-label renames do not enqueue work. At most one active rule applies to a status; rule edits affect future transitions. The recorded transition and UTC base date, selected revision, initiating identity/membership, durable job and logged PGMQ notification commit with the deal change and audit.

Jobs owns orchestration state; CRM owns typed recipe inputs and completion references. A worker resumes only the sealed actor record loaded by the Jobs DAO, retains no bearer token and rechecks the current identity/membership, module, parent, configuration and Tasks permissions. Retired definitions and superseded transitions block execution. Operator resume never substitutes the operator for the initiating user. Completion, created tasks/checklist/links/history, audit and queue acknowledgement commit together.

Claims use a 120-second database lease, a random fence and a durable attempt count. Queue visibility commits before acquiring the job lock to avoid inverse queue/job lock order. Execution takes the workspace lock before the job lock and refuses stale fences. Transient database failures delay retries exponentially; five attempts exhaust the current run. Explicit resume starts a new run while retaining all history. Domain/authority failures block. Cancellation retains evidence. Disabling CRM blocks even unclaimed work in the same transaction, and re-enabling does not resume it. The enabled-state check also applies to replayed resume requests.

Safe job headers and ordered attempt history remain available to authorized operators while CRM is disabled. Deal/checklist links appear only after independent CRM authorization. History uses a monotonic sequence rather than transaction-start timestamps. All list/history queries have bounded cursor pagination. API/OpenAPI, CLI, MCP and SSR expose rule configuration and job list/detail/history/resume/cancel; web actions retain invalid/conflicting drafts and request identities.

The separate Compose worker has no public port, uses the runtime database role, runs without root privileges and publishes a local heartbeat. Setup stops it before migrations and starts it only against the expected schema. It receives no Auth signing secret. Restore/reconciliation tooling remains a separate gate.

The isolated journey passed atomic enqueue rollback, pinned rule execution, duplicate delivery, current authority and identity revocation, retirement, disable/resume/replay, retry/exhaustion/cancel, stale fencing, actual worker death after claim and after staged writes, ordered overlap history, scoped outcome links and all interfaces. Review findings about retirement, resume replay and event ordering were addressed with behavioral regressions. Full fresh-install and upgraded-database acceptance, static/unit checks, the primary update and gateway smoke all passed. Targeted review confirmed the findings resolved. The retained upgrade fixture exceeded the old Contacts pagination test cap; that probe now uses its unique run filter while still checking multiple pages and duplicate-free results.
