# CRM activity increment

An activity records something that happened, independently of actionable Tasks. Workspace-owned activity types specify supported behavior explicitly: a note or a logged interaction. Labels are editable and never imply executable behavior. Note/call/meeting are starter-template suggestions rather than permanent database types. Each type has stable identity, order, archive state and version; its semantic behavior is immutable, so changing meaning creates a new definition rather than rewriting past records.

An activity has subject/body, an offset-qualified occurrence time, a responsible staff membership, type, archive state and version. A logged interaction can carry bounded duration metadata; a note cannot acquire interaction behavior simply through its label. Activity revisions retain the type label/behavior and content that were saved at the time. Editing or archiving appends history in the same transaction as audit/retry. No automatic deletion runs.

Use exactly one typed contact, opportunity or deal anchor with workspace-qualified foreign keys. CRM owns activities even when anchored to a shared contact, so disabling CRM hides them while Contacts and Tasks remain usable. Current activity read/action scope and independent anchor visibility are both required. Contacts owns canonical/alias resolution; merges preserve original references and activity history without making hidden aliases visible. Creating or restoring an activity requires an active anchor; history remains readable for archived anchors when otherwise authorized.

The timeline combines authorized activity, task/link and status history through owning-module projection interfaces. It must apply each source's permissions before public pagination and must not reveal hidden IDs or counts. Use bounded batches rather than one cross-module query per item. Activities do not implement mailbox synchronization, calendars, meetings or sending messages.

Validation must cover type rename versus behavior, retired definitions, offset/date parsing, independent activity/anchor scopes, contact aliases, archive/edit/retry concurrency, transaction rollback, disabled CRM, bounded pagination and equivalent API/CLI/MCP/SSR behavior.

Implementation contract: occurrence timestamps accept RFC 3339 with an explicit offset, normalize to UTC at PostgreSQL microsecond precision, and reject leap seconds and dates outside years 0001–9999. Activity pages are scoped to a typed anchor and use creation-time/ID cursors; occurrence time is recorded business data, not an implicit reordering of a paged feed. Type configuration pages use configured position, then creation time and ID. Contact family IDs come from Contacts before indexed CRM candidate reads; original and canonical visibility are rechecked in bounded projections. Anchor names and canonical IDs are current projections, including on history/retry responses; activity content/type snapshots remain immutable.
