# Forms checkpoint

November 1, 2026; schema version 30. Forms is the optional application from Milestone 2: versioned definitions, conditional questions, public and embedded submissions, notifications, export and the built-in Forms-to-CRM inquiry recipe. It works with CRM disabled.

## Behavior and contract

Staff manage forms through web, API, CLI and MCP. Drafts are editable; publishing snapshots the draft as an immutable version and starts accepting answers. Closing, reopening, archiving and restoring use optimistic versions and idempotent retries. Restoring leaves a form closed until it is reopened. Field and option keys are the stable identity used by submissions, conditions and mappings; labels may change freely. Conditions refer to an earlier choice or checkbox question, so they cannot cycle.

The web builder needs no raw JSON and no scripting. The whole draft is one form and every button (add, edit, move, remove, options, conditions, save, publish) submits it, so a change never discards other edits. Keys are derived once from the label. A rejected change shows its reason and keeps the draft as it was before that button; a stale version also offers a discard link. "Save and publish" saves first; if publishing then fails the draft stays saved and the page says so.

`/f/{public_key}` and `/f/{public_key}/embed` render the published version without a session. The page reads no session cookie, the gateway strips `Cookie` on `/f/*`, and the API call carries no credential, so a public key reaches only its own form. Reads expose only the name, description and published definition. Without scripting every question is visible with a note saying when to answer it, answers left in questions that end up hidden are dropped by the server, and required conditional questions are validated by the server. With scripting, questions show and hide as answers change. A hidden field holds a random submission key; a retry of a committed key returns the confirmation again and never duplicates, including after the form closes or a new version is published, because it is compared with the version it answered. The same key with different answers is a conflict. Answers beyond the stored limit are rejected as invalid before reaching the database constraint. The gateway forwards the client address through the server-rendered page, so throttles apply per respondent rather than to the web server.

Only the embed route sends `Content-Security-Policy: frame-ancestors *`. `/f/{public_key}` sends `frame-ancestors 'none'` and `X-Frame-Options: DENY`. Every other route sends the same refusal, added to any policy the route sets itself.

Submissions keep the original visible answers with the version answered, and staff read them against that version's labels. The summary counts choice and checkbox answers for the published version's questions. Notification recipients must hold workspace-wide `forms.submissions.read`; delivery rechecks it, and the email holds a link but no answers.

The recipe maps published questions to a contact name, email and phone, a pipeline and stage, an optional owner and a title prefix. Submission, run and durable job commit in one transaction. The worker uses Contacts intake: one exact match is reused, no match creates a contact, and ambiguous or identifier-free input waits for review with the run shown as **Needs review**. Public answers never edit an existing contact. Each submission records one run, contact association and inquiry. Failures are job states shown as **Failed** with their reason: invalid mapping (`invalid_input`), missing permission (`authority`), disabled application (`module_disabled`), exhausted retries. Retry resumes the same run. Runs use the current permissions of the member who activated the recipe.

Export adds `forms`, `form_versions` and `form_submissions` to the business export with `forms.read` and `forms.submissions.read`; submissions also need `forms.read`. Web staff can download a form's submissions as CSV. That route reads through the permission-checked submissions API, neutralizes text that a spreadsheet would evaluate with a leading apostrophe (`=`, `+`, `-`, `@`, including after whitespace and in full-width forms; numeric answers stay numbers), and stops rather than ending as if complete when a later page fails. Without `forms.read` the CSV holds answers as one JSON column.

## Evidence and limits

`scripts/forms_smoke.py` runs the core journey with CRM disabled and covers conditional validation, retried and conflicting keys (after closing and after a new version), oversized input, export pages and their permissions, CLI/MCP parity, recipe reuse and independent inquiries, trusted contact data unchanged after a repeat submission, visible ambiguity, an invalid mapping at run time, missing permissions, CRM disablement, rollback/retry without duplicates, a stopped worker and an expired lease after commit, deactivation, and SMTP notification without answer content.

`scripts/forms_browser_smoke.py` drives real HTTP through the gateway with a scripting-free client that submits only what a browser would: application selection, builder operations, publish, cookie-free direct and embedded submission, framing headers, forged origins, session gates on non-public paths, version-true detail, CSV formula neutralization and permission checks, close/reopen, notifications, export selection, recipe states with retry, per-respondent throttles and archive. Both run in `scripts/acceptance.py`. Conditional show/hide and a submission from a cross-site frame were additionally checked once in headless Chrome, along with refusal of the non-embed page in a frame; that check is not part of the repeatable suites.

Not supported: file-upload questions, per-respondent editing or resuming, payment, CAPTCHA, spam scoring beyond per-client throttles, an allowlist of embedding sites, or multi-page forms. Conditions test one earlier question. Publishing does not check an active recipe's mapping against the new version; a mapped question removed by a later version becomes a visible run failure. Retrying that run keeps failing because it keeps its mapping revision and answered version; its answers stay readable. Recipes apply to new submissions only. Recipe mappings, delivery records and retry keys are not in the business export. Permanently deleting a contact referenced by a recipe run is refused as a retained business reference, and submitted answers are not erased with a contact. CLI and MCP have no CSV command; they use the JSON export.
