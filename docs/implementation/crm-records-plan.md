# CRM records implementation plan

Next increment after staff administration: application selection and the first usable opportunity/deal workflow. This document makes the accepted model concrete; it is not a completion claim.

The registry exposes CRM as optional and Contacts as shared foundation. Missing CRM enablement means disabled. An administrator explicitly enables it; disabling preserves data and blocks CRM reads/writes. Transactions that modify CRM lock the workspace before checking enablement, preventing a concurrent disable from being bypassed. Re-enabling never replays prior work.

Configuration uses separate pipeline/stage and deal-category/status definitions with stable workspace-qualified IDs. Stages have open/won/lost semantics; deal statuses have independent lifecycle meanings. Definitions can be renamed, reordered and archived. Renames do not create record transitions. A semantic meaning already used in history cannot be edited; create a new definition and explicitly transition instead. Archived definitions remain visible on historical records but cannot receive new assignments. A one-time standard template is optional and removable; reinstalling requires an explicit operation, never an update side effect.

Opportunities and deals remain separate tables and operations. Each has a title, notes, active assigned staff owner, exact optional amount/currency, optional local dates, archive state and expected version. Each opportunity belongs to a pipeline/stage. Deals use their own category/status and have an optional origin opportunity. Multiple deals may reference one origin; direct deals remain valid. Creating a deal does not implicitly win its opportunity, and winning an opportunity does not complete a deal.

Participant and label assignments use typed tables, workspace-qualified foreign keys, and owning-module authorized interfaces. Reading a sales record does not expose contacts or organizations outside the caller's independent visibility. Confirmed contact merges preserve CRM associations through canonical references or aliases, with current scope reapplied. Record histories preserve transition labels and meanings at the time of the transition.

Every read checks module state and action scope before pagination. Every mutation checks action/read authority, current active owner, definition compatibility, expected version and the scoped idempotency key; it commits data/history/audit atomically. CRM permissions are explicit supported grants added to the administrative catalog. No role-name bypass and no automatic external-customer access.

Acceptance proves independent lifecycles, multiple deals from one opportunity, direct deal creation, custom-definition rename versus transition, invalid pipeline/status and cross-workspace links, workspace/assigned isolation, concurrent edits/retries, module disable/re-enable without deletion, and web/API/CLI/MCP parity. Tasks, activities, coordination templates, exports and operations release gates follow as separate connected increments and remain unchecked until tested.

Implementation choices for this increment: stage parent/outcome are immutable from creation, and each deal category owns its statuses. A deal's optional origin is selected at creation; ordinary edits never rewrite its provenance. Record writers serialize on the workspace row for straightforward module-disable and definition-edit correctness; this is a deliberate per-workspace write-concurrency limit to measure before release. Estimates follow the canonical `numeric(20,6)` contract and a pinned supported current/historical ISO catalog, documented in [currency catalog](crm-currency-catalog.md). Record and staff-directory pagination uses creation/join timestamps plus IDs, rather than relying on random UUID order.
