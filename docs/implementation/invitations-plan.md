# Staff invitation implementation plan

Workspace access administration owns pending, expiring and revocable staff invitations. Creating or changing an invitation requires current workspace-wide access administration and access-read permissions, the same authority that can already assign staff roles. Store a snapshot of the invited role IDs and versions; acceptance fails if a role was archived or changed, or the inviter no longer has current authority. No invitation assigns external/customer access.

An invitation has a random ID/nonce, intended Auth email, expiry, inviter, role snapshot, version and retained acceptance/revocation history. A domain-separated HMAC-SHA256 derivation from the installation secret produces a distinct key for purpose-bound invitation tokens. It is not the Supabase JWT signing key. Setup materializes it privately for the API; coordinated backup preserves the source secret and derived key consistently. Do not persist bearer links in audit or replay records; reconstruct authorized pending links from retained invitation metadata. Expiry and revocation always consult current application state.

Acceptance requires a verified first-party identity and the current confirmed email obtained from Supabase's user endpoint. Never trust caller metadata, the contact catalog, or a stale JWT email claim. Auth's email identity normalization is separate from case-preserving contact identifiers. Application users and provider mappings are created only after proof and invitation checks succeed. Atomically accept the invitation, establish or retain an active membership, add the invited roles and record audit history. An old invitation must not reactivate a removed or suspended membership. Concurrent/repeated acceptance must not create duplicates or repeat grants after revocation.

Deliver copyable links and the browser acceptance flow first, then controlled new-identity setup and configured email delivery. An Auth account alone grants no membership. Existing identities sign in through the normal flow. New identities require invitation-controlled provisioning and email verification; there is no public signup. A failed external provisioning/delivery step leaves the pending invitation retryable without granting business access or resetting an existing identity's password.

Expose administration and acceptance through the HTTP contract, CLI and MCP; browser pages use those same operations. Tokens and passwords travel only in protected bodies/private token files and HttpOnly pending cookies, never telemetry or process arguments. Keep arbitrary redirect targets out of the flow. Verify the approved real HTTP/browser/CLI/MCP seams: current grant denial, recipient mismatch, unconfirmed identity, expiry/revoke, role changes, suspended membership, concurrent retries, atomic audit rollback, existing/new identities, SMTP failure and final-administrator invariants. Review both axes and include this slice in the user's requested single remaining commit.

## Delivery implementation

An explicit, idempotent send operation atomically records a typed invitation-delivery job and audit event. The normal job worker rechecks the original actor, inviter, current role versions, invitation state and expiry before calling private Auth. It creates an unconfirmed Auth identity only when absent, never updates an existing password, and requests a recovery email for ownership proof. The callback accepts only the installation's invitation route as pending context; GET previews never verify email or grant access. The recipient then sets a password and explicitly accepts the separately scoped invitation.

Delivery is at least once: a crash after SMTP acceptance may send another message on retry. SMTP/provider failures retry five times with at least 60 seconds between attempts, then require explicit operator resume. Expired/revoked invitations or lost authority block delivery. External calls never grant suite membership; only verified acceptance does. Generic job lists omit private invitation details; typed details require current access-read permission. Disabled email keeps private copyable links available for existing identities.

Pinned provider references: [Auth admin creation](https://github.com/supabase/auth/blob/v2.196.0/internal/api/admin.go) rejects duplicate email without changing the identity; [recovery](https://github.com/supabase/auth/blob/v2.196.0/internal/api/recover.go) sends proof through the configured mailer. Integration journeys verify the actual provider behavior, including existing/unconfirmed identities and SMTP failure.

## Integration hardening

The full regression exposed service restarts losing the derived mail-enabled flag. All callers now receive that flag from the canonical configuration function, with a regression test. A fixture also advanced its schema through a rerun of the live-mounted migrator while retaining an older application image. Migration sources are now copied into the built migrator image, so rerunning an existing installation's migrator cannot consume newly edited checkout migrations. Deployment still builds all images together and quiesces callers before migration. Do not change migration files during deployment; applied files remain immutable.
