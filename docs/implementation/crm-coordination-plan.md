# CRM coordination implementation sequence

The first connection is an independently authorized task linked to an opportunity or deal. CRM owns typed opportunity/deal task links; Tasks owns task content and lifecycle. A relation never grants read or write permission on either record. Link list/history applies both scopes before pagination. CRM can create a task and its association atomically by invoking a Tasks-owned transaction operation; it never reads or writes Tasks tables directly. Disabling CRM hides these links while shared Tasks remains available.

Link actions need the parent read and task-link management permission, and independent task read. Creating a follow-up additionally needs Tasks create/read and a permitted active assignee. Existing task linking does not edit the task. Parent optimistic version protects link changes; archive retains references but denies new links/restoration until both records are active. Individual end/restore operations preserve evidence and cannot erase hidden links.

The next coordination journey will apply a pinned workspace template revision to a deal. It creates ordinary tasks and an ordered checklist/milestone instance, with stable per-instance task references. Editing/removing the template never rewrites or deletes existing instances. Supported behavior is bounded configuration: task title/notes, explicit assignee rule, calendar due offsets, ordered milestones and a configured deal-status trigger. A general workflow engine is outside this increment.

Task creation from a configured status transition will exercise PGMQ: material change, audit, job metadata and enqueue are atomic. The worker will recheck enabled modules and current initiating authority, use leases/fencing and durable retry/exhaustion state, and expose blocked/exhausted work. Resume is explicit after module re-enablement. No caller-supplied flag can create system authority.

Activity definitions and logged interactions remain CRM-owned. The timeline composes authorized activity, task/link and status history through their owning interfaces. Templates, activity types, supported configuration behavior and instance revision rules are implemented before the first starter-template installation is advertised.

## Concrete template composition

Implement shared task types and versioned task templates in Tasks. A task template revision records its type, title/notes, assignment rule (initiating staff member, contextual record owner, or a fixed active membership) and a bounded calendar-day due offset. Material edits create a new immutable revision. An application supplies its independently authorized contextual owner; Tasks still checks current create/read assignment authority. Callers choose an explicit base calendar date rather than deriving deadlines from an ambiguous local timestamp.

CRM coordination template revisions contain an ordered, bounded checklist of named items, each referencing a pinned Tasks template revision. Applying a revision to a deal creates ordinary Tasks and CRM task links in one transaction, plus an instance that retains the chosen revision and item identities. Checklist progress is derived from independently readable task lifecycle; it is not a second editable copy of task status. Template rename, replacement or archival never rewrites those tasks. A hidden task must not expose its title, status or aggregate completion count.

The first bounded trigger applies a pinned coordination revision on a configured deal-status transition. Capture the triggering transition, selected revision, initiating user/membership and base date atomically with the job; a unique transition/trigger identity prevents duplicate scheduling. Execution rechecks current authority and module state. Blocked or exhausted jobs require visible resolution; re-enabling CRM does not silently resume them. External mail or arbitrary executable actions are not part of this recipe.

The removable starter package will copy useful workspace-owned sales/deal definitions, activity types, task templates and one coordination checklist. Installation is explicit and versioned. Upgrades never reinstall an intentionally removed package. Removing it retires its definitions without deleting business instances or historical revisions; existing independently owned workspace edits are not silently overwritten.

## First checklist instance

A coordination revision contains at most 25 ordered items. Each item has a stable revision-local ID, a label and a pinned Tasks template revision. Publishing an edited specification creates a new revision and new item definitions; instance items keep their original IDs. There are no implicit dependencies or additional completion states: a checklist item reports its independently readable task's current status. Hidden task details and aggregate progress remain unavailable rather than implying completion.

An apply command includes the deal's expected version, the chosen coordination revision and a base calendar date. It requires independently scoped `crm.deals.coordination.apply`, deal read, task-link management, configuration read and the independent Tasks configuration/create/read grants. The contextual owner comes from the current permitted deal. Create the instance, every task, typed link, per-item reference and audit record in one transaction; any failure rolls everything back. A repeated operation key returns the original instance only after checking current authority for the parent and every task included in that result. Ordinary instance reads may project only visible items without exposing omitted counts.

An instance is retained when its template is archived. A task's lifecycle is edited through Tasks, while ending a CRM link does not cancel or delete the task or its instance evidence. Instance views must distinguish a historical ended link from a currently linked task. Archiving a parent denies new application but preserves existing permitted instances and history.

Application results contain at most 25 full task snapshots. The persisted retry-result bound is 2 MiB to support maximum-sized task notes; request fingerprints retain their 64 KiB bound. Instance collections return summary headers only, while a detail request projects independently visible Tasks.
