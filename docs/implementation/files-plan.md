# Initial shared Files capability

Files owns immutable uploaded bytes and metadata independently of CRM. For the small local first release, store bounded content in PostgreSQL alongside metadata, using a separate content table and the ordinary owning SQLx DAO. This keeps file creation, audit and retry semantics atomic and makes coordinated PostgreSQL recovery include actual file bytes. Do not introduce an untested object-store service or filesystem/database dual-write boundary. Larger objects and external storage can later use a versioned storage adapter with explicit migration and recovery checks.

Initial files are limited to 8 MiB. A file has a workspace, stable ID, responsible membership, original display filename, supplied media type, byte length, SHA-256 digest, notes, archive state, timestamps and version. Uploaded bytes are immutable; changing content creates a new file. Original filenames are display metadata, never filesystem paths. Validate names, type, notes and size. Downloads use attachment disposition, no-store and nosniff; no inline execution or preview claim. Verify stored content length/digest before returning it.

Use separately supported `files.read`, `files.create`, `files.update` and `files.archive` actions, each with workspace/assigned record scope. File ownership does not imply permission. Metadata listing and content download enforce current membership and file visibility. Archive is the default removal action; no automatic deletion. Upload retry evidence stores the byte digest/length and metadata, never another copy of content in request/audit payloads. Required writes and file bytes commit with audit/replay evidence or roll back together.

Provide upload/list/get/download, metadata editing and archive/restore through HTTP/OpenAPI, CLI, MCP and browser. HTTP carries bounded upload data; local CLI/MCP adapters may read an explicitly selected local file and write a private, non-overwriting download artifact. They call the API and never access the database. The selected initial scope is a shared file library; typed business attachment associations remain future owning-module work. Linked business records will use typed module-owned relations with workspace-qualified foreign keys and independent file/parent visibility; attachment association must never grant broader file access. Implement and document the selected associations rather than claiming generic arbitrary-entity support.

Exports must include a file metadata collection and an explicit content retrieval path with digest checks. A coordinated backup must preserve both metadata and content and verify hashes after isolated restore. Test upload and download byte fidelity, limits, malformed encoding, independent read/create/edit/archive grants, foreign-workspace references, archive behavior, stable retry/changed-body conflicts, concurrent retries/edits, late-audit rollback, private artifact handling and all client interfaces. Measure the resulting database/archive footprint before claiming suitability for large media libraries.
