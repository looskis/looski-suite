# Deal-status coordination and durable execution

This increment implements the first bounded recipe from ADR 0004 and the CRM coordination plan. An active workspace-owned rule binds a deal status to one immutable coordination revision. Rules have stable IDs, names, archive/version metadata and an explicit UTC calendar base-date policy (transition date). Configuration requires CRM manage/read, Tasks configuration read and independent coordination-revision validation. Rule changes affect future transitions only. At most one active rule per status keeps the first recipe predictable; no arbitrary code or external effects.

An actual deal status transition schedules one durable job per rule. Initial creation in a status is not a transition trigger; unrelated deal edits and status-label renames do not enqueue. CRM records the selected rule/revision, transition audit/identity, base date, deal/status and initiating identity/membership in the same transaction as the change, audit, job and PGMQ send. A unique rule/transition identity and ordinary operation retry prevent duplicate scheduling. Scheduling requires only the original deal-change authority; execution independently checks the current initiating identity/membership and all permissions required by checklist application. Missing execution authority becomes a visible blocked job rather than losing a valid deal update.

Foundation Jobs owns persistent state and a logged PGMQ queue; CRM owns recipe configuration/payload validation and calls Tasks only through its transaction provider. The worker resumes a recorded actor from durable records, never accepts caller-supplied system authority, and does not retain bearer tokens. Execution rechecks module state, current parent/assignment/configuration permissions and active definitions. A moved/archived deal or retired definition blocks stale work. Job completion and resulting instance/task/link/audit writes share a transaction; durable completion prevents duplicates beyond the normal request-key retention window.

Claims increment a durable attempt counter and issue a random fencing token plus a bounded database lease. The execution transaction obtains the workspace lock before the job lock, verifies the claim and lease, invokes the module operation, and records completion/queue deletion atomically. A crashed claim is available after lease expiry; stale claim holders cannot commit. Transient database failures roll back business work and record a bounded delayed retry; five attempts exhaust the job. Domain/authorization/module failures become blocked. Errors expose stable categories, never SQL/provider details or task content.

Module disablement marks pending jobs blocked in the same workspace-serialized operation, including jobs that have not yet been claimed. Re-enabling never resumes them automatically. Explicit resume keeps the initiating actor and immutable recipe input, checks operator authority/version, and sends a new queue message; it does not manufacture the operator's authority for execution. Cancel is recorded and never removes historical evidence.

Workspace-wide jobs read/manage scopes allow operators to see safe status headers even while CRM is disabled. No task payload or hidden parent content is included in these headers. Detail views add a deal/checklist link only through CRM-owned authorization. Attempt history uses a monotonic sequence, independent of transaction-start timestamps. API/CLI/MCP/SSR expose bounded job listing/detail, attempt history, resume/cancel and rule configuration. The first worker is a separate health-gated Compose service with no public port. Setup quiesces it before migration and restore leaves it stopped until reconciliation.

Acceptance uses real PostgreSQL/PGMQ: enqueue rollback, one job per material transition, renamed statuses/ordinary edits produce none, pinned rule edits, expired claims/fencing, duplicate delivery, crash after claim and before commit, atomic completion, independently revoked actor/action/assignment, disable/re-enable before claim, explicit resume/cancel, transient retry/exhaustion and all interfaces. Background processing is stopped only on the isolated fixture for deterministic claims, then restored. Fresh/upgraded full regression and packaging readiness gates remain required.
