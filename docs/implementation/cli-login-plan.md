# CLI/MCP login implementation plan

The CLI and local stdio MCP adapter need a first-party session without asking for a password in a terminal, exposing private Auth routes, or running a localhost callback server. Use the authorization code flow with PKCE (S256, [RFC 7636](https://www.rfc-editor.org/rfc/rfc7636)) and a copy/paste code. This is first-party session acquisition, not delegated OAuth: the resulting token carries the user's ordinary current permissions, has no `client_id`, and does not replace future connected-application grants.

`looski login` generates a 256-bit verifier, its S256 challenge and a random state. It prints a link to the installation's `/cli/authorize` page and tries to open it. The SvelteKit page requires a browser session. Without one it sends the person to sign in and back; the login return target must be a same-origin absolute path and never `/login`, `/logout` or `/auth/*`. The page names the installation origin, the signed-in email and any device label, marked as reported by the device, and warns against approving a link someone else sent. Approve and Cancel are same-origin POSTs. Approval calls Rust with the browser's bearer token and shows `code#state` once in the no-store response; the code never enters a URL, log or telemetry. The CLI checks the returned state and exchanges the code with its verifier.

Rust owns the authorization record. Approval requires an active application user mapped to the verified identity and stores only the SHA-256 of a 256-bit random code, the challenge, an optional label and a five-minute expiry. At most five unexpired, unconsumed approvals may exist per user, serialized with a per-user advisory lock. Exchange is public: it locks the row, then rejects unknown, consumed or expired codes using wall-clock time after the lock. A wrong verifier, an inactive user/identity or an issuer mismatch consumes the code as rejected, so a leaked code cannot be retried. A valid exchange mints a new Auth session while holding the lock and records it as issued with its session ID. An Auth outage rolls back and leaves the code usable until expiry; an unrecorded session is revoked rather than returned. Every failure has one `invalid_grant` answer.

Auth has no admin "create session" route. The pinned [admin generate-link](https://github.com/supabase/auth/blob/v2.196.0/internal/api/mail.go) handler produces a magic-link token hash without sending mail, and [POST /verify](https://github.com/supabase/auth/blob/v2.196.0/internal/api/verify.go) with that hash returns a normal session. Rust first reads the Auth user by stable subject, so an email alone never selects an account and an unknown email is never auto-created. Generating the link replaces any outstanding recovery/magic-link token for that account. The new session has its own session ID and refresh-token family, independent of the browser session.

Because raw `/auth/v1` stays private, Rust also proxies refresh (`/token?grant_type=refresh_token`) and logout (`/logout?scope=local`). Refresh is accepted only for sessions recorded as issued by a CLI exchange; browser sessions keep refreshing through SvelteKit. Logout verifies the bearer session and revokes only that session. Public exchange and refresh endpoints have per-client fixed-window limits (20 exchanges and 60 refreshes per minute) keyed on the gateway's forwarded address, with a bounded table. The gateway sends exactly one `X-Forwarded-For` entry: Cloudflare's `CF-Connecting-IP` when the request arrives from a private-network peer (the tunnel connector), otherwise the direct peer, so tunnel visitors get separate buckets. Auth's own limits still apply.

User-level security events (`cli_login.authorized`, `cli_login.exchanged`, `cli_login.rejected`, `cli_session.logout`) go to a new append-only `suite.security_events` table in the same transaction as the authorization change. Workspace audit events remain workspace-scoped. Refreshes are not audited, matching browser refresh. Approval is deliberately not idempotent: a retried POST creates another bounded, independent code, because the original code cannot be reconstructed from its hash.

Clients store the session per installation origin: the macOS Keychain where available (through the already-locked, maintained MIT/Apache `security-framework` crate rather than an additional wrapper), otherwise a private file written by atomic rename. Supabase refresh tokens rotate and reuse outside a short interval revokes the family, so refresh happens under an exclusive per-origin file lock (`std::fs::File` locks) and rereads the store first. Requests refresh two minutes before expiry and retry once after a 401. A rejected refresh deletes the stored login and asks for `looski login`. `LOOSKI_ACCESS_TOKEN_FILE` keeps precedence for externally managed sessions.

Verify the real browser/HTTP/CLI/MCP seams on an isolated fixture: login return path and off-origin rejection, CSRF, single use, wrong verifier, expiry, suspension, hashed storage, audit, refresh rotation and replaced-token rejection, browser-session refresh refusal, pasted foreign state, private storage, concurrent CLI/MCP refresh, 401 retry, independent logout, membership removal and the approval bound.
