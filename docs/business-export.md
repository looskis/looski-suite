# Business export

Export preserves permitted business records as versioned JSON. It requires `workspace.data.export` and the selected collection's ordinary read permissions. The catalog lists dependent read permissions for relationships. Workspace/assigned read scope still applies to every record and related contact, organization or task. Revoked authority stops subsequent pages; disabled CRM cannot be exported through its ordinary routes.

In a workspace, open **Export data**, choose a collection and lifecycle, and supply its parent ID when requested. Preview and download each page; follow **Next page** until the end. Each file holds at most 25 top-level records. The JSON manifest identifies the workspace, selected collection/parent/lifecycle, application and format versions, and live-read consistency. `items` contains the documented public business projections. `next` is either the complete next request or null. Preserve manifests when combining pages.

For an agent or script, use `GET /api/v1/workspaces/{workspace_id}/exports/collections` and `POST /api/v1/workspaces/{workspace_id}/exports/page`. The POST is read-only and does not need an idempotency key. The CLI exposes `looski export ... collections` and `looski export ... page` (selection JSON on stdin); MCP exposes `export_collections` and `export_page`. All use the same business boundary.

For example, select `{"collection":"contacts","archived":false}`. To build a complete private file for that selection, save the selection in a file and run:

```sh
python3 scripts/export_collection.py --api-url http://localhost:58888 \
  --workspace WORKSPACE_UUID --token-file /private/path/access-token \
  --output /private/path/contacts.json < selection.json
```

The collector invokes the supported CLI, follows all continuations and writes a mode-0600 temporary file. It publishes a new output path only after completion and never replaces an existing file. Fetch, validation or page-limit failures remove the temporary file. The package has `format: looski-business-package`, version 1, the original pages, counts and `complete: true`. Use `--binary` for an installed CLI and `--max-pages` to adjust the default 10,000-page ceiling. Protect exported files like the underlying business records.

Collections cover Contacts/Organizations and their current or ended relationships, tag definitions and assignments, opportunities/deals and their stage/status histories, custom pipelines/stages/categories/statuses, participants, shared Tasks/history/types/templates/revisions, CRM task links, logged activities/history/types, coordination templates/revisions/rules/instances with checklist item-to-task mappings, and Forms: complete forms with drafts (`forms`, `forms.read`), a form's immutable published versions (`form_versions`, `forms.read`) and its original submissions with their version and any recipe-run state (`form_submissions`, `forms.submissions.read` plus `forms.read`). Forms collections work with CRM disabled and stop while Forms is disabled. Parent-specific collections preserve stable parent IDs in the manifest and stable record IDs in rows. Ended contact organization history includes independently visible merged aliases with their original contact IDs. Export current and archived/ended selections separately, and collect related collections explicitly; downloading Contacts does not silently include CRM or Tasks.

CMS adds `cms_content_types` and `cms_media` (`cms.read`), and `cms_entries` and a given entry's `cms_revisions` (`cms.drafts.read`, also needing `cms.read`). Entries include their drafts and what is published; revisions are immutable and include the fields they were saved under. `cms_media` is metadata: its bytes belong to Files and are reachable through each record's `file_id` with Files permissions. Public keys are exported because they are a type's address.

Projects adds `projects` (`projects.read`, with archive selection), and for a given project `project_members`, `project_columns`, `project_cards` (with ended selection for tasks taken off the board) and `project_comments`. Cards and comments also need `tasks.read` and list only tasks visible to the exporter. Comments export their source text and parsed blocks; a removed comment exports as a marker with no text. An assigned-scope exporter sees only projects they belong to, and `source_deal_id` appears only with independent read access to that deal. Collections work with CRM disabled and stop while Projects is disabled. Task records are exported through the Tasks collections; recipe configuration and runs are not exported.

The knowledge base adds `knowledge_collections` and `knowledge_documents` (`knowledge.read`, with archive selection), and for a given parent `knowledge_collection_members` and `knowledge_revisions`. Every collection lists only what the exporter reaches: a restricted collection needs listing or `knowledge.restricted.access`, and a hidden parent answers 404. A document exports its source text, parsed blocks and linked previews as this exporter may see them; a revision also needs the collection it was written in. Exporting does not widen access, so an exporter who is not listed produces an incomplete archive of restricted material by design.

This format represents supported public projections, not every internal database row. It excludes authentication credentials/sessions, staff invitation links, administrative audit/replay payloads, intake evidence, queue internals, diagnostic logs and internal starter-package bookkeeping. Forms-to-CRM recipe mappings, notification delivery records and submission retry keys are not exported. Participant/task-link change-event history remains available through its ordinary history APIs; export collections contain their current and ended records. General custom fields, communication/message export and file bytes are not yet implemented. Do not claim full installation portability or recovery from these files. Use coordinated backups for that purpose.

JSON retains text and decimal strings exactly, including values beginning with `=`, `+`, `-` or `@`; it is not a spreadsheet-oriented CSV. A later spreadsheet conversion must apply its own formula-injection protection, as the staff **Download CSV** of a form's submissions does. Each page is a live authorized read, not a consistent database snapshot. Concurrent edits may change later pages; `complete` means all pages of the selected live collection were received, not that the entire workspace was captured at one instant.

## File content

The `files` collection exports authorized metadata, including byte length and SHA-256, with explicit active/archived selection. It does not embed bytes. Retrieve each authorized `files/{id}/content` response separately and verify its digest, or use the private CLI download command described in [Files](files.md). This is a live read; typed business attachments are not implemented.

Helpdesk adds `helpdesk_tickets` (active or archived) and `helpdesk_messages` (requires the ticket as `parent_id`). Both require `helpdesk.read` in addition to the export permission and apply current assigned/workspace scope. Ticket contact associations and article previews retain their independent read checks. The message export includes internal notes because this is a staff export; it is never a customer endpoint. Access codes, their hashes and retry fingerprints are excluded. Messages are immutable and paginated chronologically.

Time tracking adds `time_entries` and `time_budgets`, with active/archive selection and `time.read`. Assigned reads export only the member's entries; budgets require workspace-wide reads. Project references retain Projects visibility. Integer `duration_ms` values preserve precision; running entries are measured at the page transaction's timestamp. Multi-page exports are live reads, so stop timers first when a fixed total is needed.

Scheduling adds `appointment_types`, `appointments` and `appointment_events` (appointment `parent_id` required). All require `scheduling.read` and host/workspace scope. The appointments archive selection means cancelled reservations. Embedded Forms answers and CRM/Contacts references retain independent current authority. Private access codes, hashes and retry fingerprints are excluded.
